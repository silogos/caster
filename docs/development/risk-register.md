# Risk Register

Technical risks, their mitigations, and the phase where each is validated. Risks are re-scored after their validation phase. Sources: Phase 0 architecture analysis ([overview](../architecture/overview.md), [audio](../architecture/audio.md), [webrtc](../architecture/webrtc.md), ADRs 001–003).

| ID | Risk | Impact | Likelihood | Mitigation | Validated in |
|---|---|---|---|---|---|
| **R1** | **AudioPlaybackCapture policy blocks capture.** Apps (DRM, many music/streaming apps, some games) set `ALLOW_CAPTURE_BY_NOBODY`; capture yields silence, not an error. | Feature silently unusable for some games | High (certain for some apps) | Silent-input detection → honest UI state ("This app's audio can't be captured"); never fabricate audio; document affected-app behavior ([audio.md](../architecture/audio.md)) | Phase 7 |
| **R2** | **Two-separate-audio-track ADM limitation.** One ADM per factory; both audio sources cannot share one PC; the custom playback-capture ADM + second factory approach is unproven in our context. | Audio architecture rework | Medium | Validation spike **before** Phase 7 feature work; fallback options pre-listed in [ADR-003](../decisions/ADR-003-two-audio-track-architecture.md) | Phase 7 (spike) |
| **R3** | **MediaProjection consent & lifecycle (Android 14+).** Per-session consent dialog; FGS `mediaProjection` type must be foreground *before* projection starts; user can revoke from the status bar at any time. | Broken casts / crashes / Play-policy issues if mishandled | High | Explicit consent→service→projection ordering in the Phase 6 design; `onStop` callback as first-class stop path; lifecycle test matrix | Phase 6 |
| **R4** | **LAN ICE / mDNS obfuscation.** Chromium and recent libwebrtc publish host candidates as `*.local`; some routers/APs block mDNS → connectivity failure on otherwise fine networks. | "Won't connect" on affected networks | Medium | Mitigation ladder (resolve mDNS → disable obfuscation where possible → candidate filtering using QR `hosts[]` as ground truth) in [webrtc.md](../architecture/webrtc.md). **Phase 4 (2026-09-20): plumbing validated** — mDNS-shaped candidates traverse signaling byte-for-byte (loopback tests + live check, [features/signaling.md](../features/signaling.md)); **on-LAN resolution moves to Phase 5** (first real libwebrtc/ICE session — unvalidatable without media). | Phase 4 (plumbing) / Phase 5 (resolution) |
| **R5** | **Hardware H.264 encoder variability.** SoC-dependent availability/stability of HW H.264 (and Chromium decode paths). | Poor quality, encode failures on some devices | Medium | Offer H.264 **and** VP8; drop a codec from the offer per-device based on evidence; conservative 720p30 start; log encoder implementation via getStats | Phase 5 |
| **R6** | **WebRTC latency misses gaming expectations.** Jitter buffer, encode, and render add latency; LAN target 40–150 ms glass-to-glass. | Product unfit for purpose | Low–Medium | Measure from Phase 5 (getStats + on-screen clock method); tune (degradation preference, keyframe cadence, renderer path) based on data, not guesses. **Phase16:** the receiver jitter buffer is measured at ~90–140 ms (the dominant term, larger than the whole budget) and is **not reachable via the public API** (`jitterBufferTarget` is a floor, not a ceiling — candidate measured and rejected, [performance.md](../features/performance.md)); keyframe cadence has no knob in the pinned prebuilt (ADR-001 fork territory); glass-to-glass photo measurement (T8) still owed. | Phase5, retune 16 |
| **R7** | **LAN pairing edge cases.** Multiple interfaces (VPN/VM bridges), desktop IP change, port conflicts, firewall prompts, phone network switch. | Pairing fails intermittently | Medium | QR advertises `hosts[]` (mobile tries each); default port with ephemeral fallback; reconnect-within-TTL; user-facing messages per failure mode ([pairing.md](../architecture/pairing.md)) | Phases 3–4, 15 |
| **R8** | **Thermal load during long casts.** Sustained capture+encode heats the phone; OS throttles the game and/or cast. | Degraded sessions, unhappy users | Medium | Measurement-first ([thermal.md](../architecture/thermal.md)); profiles as user-chosen mitigation; conservative adaptation only in Phase 12; never claim "thermal safe" without numbers. **Phase16:** the profiles' fps mitigation was a placebo on device until the encoder-cap fix ( 0 fps target encode 1 fps — measured live, [performance.md](../features/performance.md)); all pre-Phase16 thermal reasoning under-states the real per-profile load. T1–T4 numbers must come from the fixed build. | Phases 11, 15 |
| **R9** | **Desktop multi-interface detection & firewall UX.** Picking the right LAN IPs; first-run OS firewall prompts differ per platform. | QR contains unreachable/missing IPs; users confused by prompts | Medium | Enumerate all non-loopback IPv4s into `hosts[]` (no picking); fixed default port so the prompt appears once; setup docs set expectations | Phases 2–3, 15 |
| **R10** | **Acoustic echo via phone speaker.** Phone speaker plays game audio while mic is on → mic re-captures it → desktop hears game audio twice. | Annoying audio on stream | High (when speaker+mic) | v1: recommend headphones when both sources are on; later: sender-side echo handling decided from measurements ([audio.md](../architecture/audio.md) limitations) | Phase 8, revisit later |
| **R11** | **OEM battery managers kill the backgrounded cast.** Non-stock ROMs (ZUI, MIUI, ColorOS, …) run their own background-app killers that may ignore an active FGS; stock Android exempts a running FGS from Doze/App Standby. | Cast dies mid-game on some devices | Medium on aggressive ROMs — **unobserved so far** | Evidence-first ladder. While a cast runs, the FGS + WifiLock ([ADR-009](../decisions/ADR-009-cast-resilience-ice-restart-wifilock.md)) self-exempt from stock battery management — so **no user prompt while unproven** (zero-friction invariant). Watch item: a plain process-death signature in logcat (no crash, no lock-screen revoke, no `bye`) on some device → then add a one-time **contextual** hint deep-linking to the battery settings (`ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS`), never a blocking dialog; the README carries the manual escape in the meantime. Evidence to date (2026-11-02): the TB321FU (ZUI) ran fully battery-**optimized** through L1 PASS and multi-hour gaming sessions with no ROM kill; its user exempted the app anyway (insurance) — so a kill there can no longer be attributed to this risk. **OEM watch list, extended 2026-11-03 (ADR-011 hotspot pairing mode):** `LocalOnlyHotspot` behavior varies per OEM/carrier — permission demands beyond the documented set (surfaces as an honest failure, never a crash), revocation at will (`onStopped` → honest state; mid-cast degrades through ADR-009), location-services-required quirks. Same rule: no workarounds until a device shows the behavior. | Watch; act only on evidence |
| **R12** | **Recovery only completes with the app foregrounded** (user-reported live 2026-11-03, TB321FU, mid-game: a dropped connection recovered only once the caster was opened). Two candidate mechanisms, both below the app layer — our scheduling is not foreground-gated (`HandlerSignalingScheduler` is a main-looper handler; the reconnect ladders — signaling, media ICE, mic (`MicReconnectPolicy`) — all run in the FGS process, which stock Android does not freeze): ① a *terminal* cast failure runs `endCast(keepSession)` → the FGS stops → the process goes cached → **cached-app freezer** (or the OEM's variant, cf. R11) parks every pending timer; foregrounding thaws it and the backlog fires at once — the exact observed signature; ② the OEM restricts *new* connections for backgrounded apps while letting established flows live (the WebSocket reconnect fails in background, media keeps flowing). | Backgrounded mid-game recovery depends on opening the app | Unknown — one live report | **Diagnosis before any fix** (evidence-first, same as R11): during a backgrounded stuck reconnect, capture `adb shell dumpsys activity processes | grep -A2 zerofriction` (frozen flag? FGS alive?) and whether the service/notification still exists. If ①-freezer post-`endCast`: the honest fix is a short-lived reconnect FGS or extending the service's life through the parked state — an architecture decision, not a patch. If ②: R11's battery-settings escape hatch is the mitigation path. No code until the capture says which. | Open — capture pending |

## Process rules

- Any new material risk discovered mid-phase is added here in the same phase.
- After a risk's validation phase, update Impact/Likelihood with measured results.
- A risk may only be closed with evidence (test result or measurement), never by assumption.
