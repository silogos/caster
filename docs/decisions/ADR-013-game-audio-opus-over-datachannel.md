# ADR-013: Game audio Opus over the DataChannel (the lighter payload)

- **Status:** accepted (2026-11-04) — amends the *payload* decision of [ADR-012](ADR-012-game-audio-pcm-over-datachannel.md); the DataChannel itself (label, in-band negotiation, unordered/unacked, drop policy, the mixer's worklet path, the track fallback) is unchanged, as are the two-PC architecture and the mic's transport

## Context

ADR-012 shipped true-stereo game audio as raw PCM over the `game-audio` DataChannel (#102, verified live) because every obtainable libwebrtc prebuilt folds stereo to mono before its own Opus encoder. Raw PCM costs a flat **1.5 Mbps** — negligible on Wi-Fi 5, but a permanent tax on the phone's radio, and the heaviest single item in a hotspot-pairing cast ([ADR-011](ADR-011-hotspot-pairing-mode.md), where the phone also hosts the network). ADR-012 deliberately deferred the lighter payload to a follow-up; that follow-up is [issue #104](https://github.com/silogos/caster/issues/104), implemented now.

The existence proof of the shape is TikTok's Live cast (reverse-engineered in #101): own capture → own MediaCodec audio encoder → own transport. Ours is the same architecture with WebRTC's DataChannel as the transport.

## Decision

The channel carries **platform-encoded stereo Opus** instead of raw PCM, with the same DataChannel, the same reliability semantics, and the same fallback chain:

- **Mobile:** `GameAudioOpusEncoder` (`webrtc/` module) — the platform MediaCodec Opus encoder (`c2.android.opus.encoder` hardware, present since Android 10; the device runs Android 16), **synchronous mode**, fed from the same ADM encoder-input tap the PCM path used. Output is one 20 ms access unit per DataChannel binary message. Availability is probed before wiring (`MediaCodecList.findEncoderForFormat`); any configure/start failure on the encoder thread rewires the tap back to the PCM sender — the encoder can only fail *before its first output frame*, and the format announce (below) is not sent until that first frame, so a failed encoder degrades to the exact pre-#104 behavior with no desktop-visible trace.
- **Bitrate: 128 kbps** (`GAME_AUDIO_OPUS_BITRATE_BPS`, named constant) — the acceptance bar is "indistinguishable from the PCM path" (issue #104), and 128 kbps stereo Opus is transparent for game content; ~12× lighter than PCM is already the win. A mobile preset knob is deliberately deferred (mobile controls; add only if a device proves it needs 96 kbps).
- **Format announce (channel payload v1):** the first text message on the channel, JSON `{"v":1,"codec":"opus","sampleRate":48000,"channels":2,"preskip":<int>}`. It is sent from the sender thread **immediately before the first Opus packet** (not at channel open): `ordered=false` would otherwise race it against the first packets, and an encoder that dies before producing output then never advertises a format it cannot serve. `preskip` comes from the encoder's csd-0 OpusHead when MediaCodec emits one, else the libopus default 312.
- **Binary frames:** one Opus packet per message — self-describing (RFC 6716), no framing header, no csd on the wire beyond the announce's `preskip`.
- **Desktop:** `game-audio-channel.ts` classifies the stream by the DataChannel's native text/binary distinction: a text announce configures a **WebCodecs `AudioDecoder`** (`codec: 'opus'`), whose decoded `AudioData` planes (f32) feed the **existing PCM worklet ring unchanged** — only the feeder changed. A binary message arriving before any announce (older mobile build) is legacy PCM, converted as before. Because `ordered=false` allows an announce to trail the first packets, binary messages are buffered until the stream classifies (a bounded few-message window; PCM flushes in order, Opus packets decode in order — SCTP still never reorders within the unreliable channel beyond dropping).
- **WebCodecs config:** Chromium's Opus decoder wants the OpusHead extradata, so the desktop **synthesizes the 19-byte OpusHead** (`OpusHead` magic, version 1, channels, pre-skip **little-endian** per RFC 7845 §3.1 — verified byte-for-byte against an ffmpeg-produced head during the live debug; sample rate LE, gain 0, mapping family 0) from the announce and passes it as `AudioDecoderConfig.description`. Explicit beats implicit: no reliance on the decoder's default-preskip behavior. The WebCodecs callbacks ride the **constructor's init object** (`new AudioDecoder({ output, error })`) — a no-arg construction throws `TypeError`, and (found live, see Costs) an escaped setup throw used to leave the stream misclassified.
- **Fallback chain (unchanged in shape, one link richer):** Opus frames → (no platform encoder / encoder fails pre-output → the mobile simply sends PCM) → (channel quiet > 3 s) dual-mono track. Both lower links already shipped in ADR-012; the desktop additionally refuses the Opus mode itself (announce unsupported / `AudioDecoder` missing / `isConfigSupported` rejects / decode error) by just never feeding the path — the quiet timer hands the track back automatically.

## Open questions resolved at implementation time

| Question (from #104) | Resolution |
|---|---|
| AAC (TikTok's exact codec) instead of Opus? | **Opus.** AAC decode needs the AudioSpecificConfig plumbed separately and platform AAC encoder configs vary; Opus is self-describing and `AudioDecoder('opus')` is universal in Chromium/Electron. Revisit only for a device whose MediaCodec lacks an Opus encoder — the fallback already covers that device. |
| Bitrate 96 vs 128 kbps; preset knob? | **128 kbps, no knob this round** (transparency is the acceptance bar; the knob is a preset-settings change on the mobile if ever needed). |
| Second, non-SM8650 device claim | The encoder probe **logs the concrete MediaCodec name** (`opus encoder: <name>`) at every cast start — the multi-device check is a log read plus one listen, not new code. |

## Consequences

- **Positive:** game channel ≈ **0.13 Mbps** steady (128 kbps) vs 1.5 Mbps — ~12× lighter, the phone's radio (and hotspot battery) get the relief; decode output lands in the identical worklet ring, so volume/mute/cable routing/probes are untouched; the desktop stats story gains a direct channel-bandwidth line (the feeder counts bytes) where PCM was only ever visible as a docs estimate.
- **Costs / accepted:** Opus at 128 kbps is lossy where PCM was bit-exact — inaudible by the acceptance ear test, and the same trade every streaming audio makes; packet loss now drops whole 20 ms packets (decoder conceals) instead of PCM slivers — equivalent class of artifact, same LAN; one new desktop failure surface (WebCodecs) that degrades to the track, never to silence; the announce adds a tiny state machine to the channel feeder (classification window), covered by unit tests on both ends. **Found live (2026-11-04, first on-device cast):** the first build played "electrical buzz" — two compounding defects, both fixed and now pinned by tests: (1) `new AudioDecoder()` without its init object throws, the exception escaped the setup path, the stream hung **unclassified**, fell to the legacy-PCM verdict after the burst window, and opus bytes were decoded as Int16 — content-modulated noise; setup is now fail-closed (`refuse` on any throw) and the page buffers channel messages synchronously so the announce cannot be swallowed by the worklet's async module load; a valid announce that trails the burst anyway reclassifies pcm → opus. (2) The OpusHead pre-skip was synthesized/parsed as big-endian — RFC 7845 §3.1 says **little-endian** (ffmpeg's own head carries `38 01` for 312); both ends now read/write LE, pinned by wire-contract tests. Both defects were found by a WebCodecs decode bench (known-good ffmpeg Opus → `AudioDecoder` with the production config) before touching the fallback chain.
- **Revisit if:** the pinned libwebrtc grows `WebRTC-Audio-MultiChannelSend` (ADR-012's retirement clause — then the whole DataChannel path retires, this payload included); or a cast proves CPU/battery-heavy enough that a 96 kbps preset matters.
